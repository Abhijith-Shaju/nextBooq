Software Design Document (SDD)

Control Plane & Onboarding (www.nextbooq.com)

1. System Overview & Purpose

The Control Plane is a standalone Next.js application distinct from the multi-tenant cafe application. It serves three primary functions:

Marketing & SEO: Public-facing landing pages to convert cafe owners into SaaS subscribers.

Tenant Provisioning (Onboarding): A self-serve wizard that securely creates new Organizations, Cafes, and Admin profiles in the database.

The Consumer Hub (Phase 2): Eventually, this same root domain will host the B2B2C public marketplace where consumers can search for tables across all participating cafes.

Hosting: Vercel (Separate project from the multi-tenant app).

Routing: Standard Next.js App Router (No wildcard middleware required).

Authentication: Shared HttpOnly cookies scoped to .nextbooq.com.

Platform Configuration: Relies on a PlatformSettings MongoDB collection for global feature flags (e.g., is_marketplace_enabled).

2. Architecture, Rendering, & Separation of Concerns

By decoupling the Control Plane from the Tenant Application (*.nextbooq.com), we achieve operational safety and optimize for Next.js rendering strategies:

Marketing Pages (/, /pricing): Statically Generated (SSG) for perfect Lighthouse scores, instantaneous global CDN delivery, and SEO.

Onboarding Wizard (/onboarding/*): Server-Side Rendered (SSR) to dynamically check session state, ensuring a secure and resumable flow.

Internal Admin Dashboard (/internal-admin): Client-Side Rendered (CSR) as it sits behind strict authentication and requires highly interactive data tables.

Security Boundary: Platform-level billing, global feature flags, and super-admin logic are physically separated from standard cafe operational code.

3. The Onboarding Workflow (Idempotent & Resumable)

The onboarding flow must execute as a strict, transactional sequence. Crucially, the flow is idempotent and resumable. If a user drops off at Step 2 and returns a day later, the system automatically routes them back to where they left off.

Step 1: Identity Creation & Verification (/signup)

User submits Email, Phone, and Password.

Verification: Requires a quick OTP/Email verification to prevent spam accounts.

API: POST /api/v1/auth/register

Idempotency: If the email already exists but the user has an empty staff_memberships array (unprovisioned), the API does not throw a 409 Conflict. It issues the JWT and allows them to resume onboarding.

Action: Creates a global User document. Issues a JWT HttpOnly cookie (24-hour expiry during onboarding) scoped to Domain=.nextbooq.com.

Step 2: Tenant Details & Slug UX Check (/onboarding/cafe)

User submits Cafe Name, Location, and desired URL Slug.

API: GET /api/v1/onboarding/check-slug?slug=coffeecove

Action: Frontend debounces user input and queries the backend to ensure the slug is unique. (Note: This is strictly for real-time UX feedback, not for data integrity).

Step 3: Subscription & Billing (/onboarding/billing)

User selects a SaaS tier (e.g., Pro, Enterprise).

API: Backend integrates with Razorpay Subscriptions (B2B).

Activation Rule: Provisioning is authorized the moment the recurring mandate is successfully authorized (e.g., UPI Autopay setup). The cafe enters a 14-day trial, after which the first automated capture occurs.

Step 4: The Provisioning Transaction (Crucial)

Once payment authorization succeeds, the backend executes a MongoDB Multi-Document Transaction:

Insert Organization (linked to Razorpay Customer ID).

Insert Cafe (Injects the unique slug and links to Organization).

Safety Net: If another user claimed the slug milliseconds prior, the database's Unique Index on slug will throw an error, instantly aborting the transaction. The API catches this and returns a 409 Slug Taken to the client.

Insert Subscription (Logs the active plan tier).

Update User (Appends { cafe_id: newCafeId, role: 'OWNER', permissions: [...] } to their staff_memberships array).

Step 5: The Seamless Handoff

Upon successful provisioning, the Control Plane redirects the user to https://coffeecove.nextbooq.com/dashboard/setup.

Auth Magic: Because the JWT cookie was scoped to .nextbooq.com, the user is instantly authenticated on their new subdomain without having to log in again.

4. Platform Super-Admin Dashboard

The Control Plane houses a hidden route (/internal-admin) accessible only to users with a specific platform role.

Role Separation: The global User document contains a top-level platform_role: 'SUPER_ADMIN' | 'SUPPORT' | null. This is entirely decoupled from the staff_memberships array used for individual cafe operations.

Core Capabilities:

Tenant Management: View all active cafes, their MRR contribution, and reservation volume.

The Kill Switch (Account vs Subscription):

The system separates subscription_status (ACTIVE, PAST_DUE, TRIAL, EXPIRED) from account_status (ACTIVE, SUSPENDED, DISABLED).

Admins can toggle account_status to SUSPENDED if a cafe violates terms of service, instantly disabling their public booking page via the tenant middleware, regardless of their billing status.

Feature Flags: UI to toggle global database flags (e.g., turning on the Consumer Marketplace).

5. Phase 2: The Consumer Marketplace Hub

When the business strategy shifts to B2B2C, www.nextbooq.com will evolve into a search engine.

Geospatial Search: The backend will expose GET /api/v1/search/cafes?lat=...&lng=...&radius=5km.

Data Separation Rule: The global search index only contains static data (Name, City, Tags, Rating, Location coordinates). Availability is never indexed globally.

Live Availability Aggregation: When a consumer expands a search result, the frontend fires a localized, real-time availability query to that specific cafe_id. This prevents the marketplace from displaying stale/ghost availability.

SEO Strategy: Dynamic routes like /city/bangalore/cafes will be generated using Next.js ISR (Incremental Static Regeneration) to capture organic Google search traffic.
