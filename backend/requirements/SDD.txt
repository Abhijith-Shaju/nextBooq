1. Architecture & System Design

1.1 Technology Stack

Frontend (Customer & Admin): React.js via Next.js (SSR for public SEO, SPA for dashboard).

Backend (API Layer): Node.js with Express.js.

Database: MongoDB Atlas (Multi-tenant document architecture).

Payment Gateway: Razorpay Route (Split payments/disbursements).

Infrastructure: Vercel (Frontend edge network), Render / AWS Elastic Beanstalk (Backend compute).

1.2 System Architecture

The system employs a Modular Monolith architecture with strict Multi-Tenant Data Isolation enforced at the middleware layer.

1.3 Data Flow (Multi-Tenancy)

Request arrives at Gateway.

Tenant Middleware extracts cafe_id from the URL slug (customer) or decoded JWT (staff).

Middleware validates subscription_status for the extracted cafe_id.

Middleware injects req.tenantId into the request lifecycle.

Service layer executes database queries scoped strictly with { cafe_id: req.tenantId }.

1.4 Time Handling Policy

All server-side timestamps are generated by the application server in UTC. Client-provided timestamps are never trusted for lifecycle events. The system stores reservation_timezone alongside the UTC dates to preserve the original business context.

2. Implementation & Logic

2.1 Core Database Schema

(For exhaustive schema definitions, refer to database_architecture.md)

Organizations: Billing entities holding Razorpay Customer IDs.

Cafes: Physical locations holding operational rules and timezone configs.

Users: Global identity pool. Staff utilize staff_memberships array for localized RBAC.

Tables: Physical inventory with can_merge_with adjacency mappings.

Reservations: Transactional records. Contains version for Optimistic Concurrency Control (OCC).

Subscriptions: Location-level licensing mapping org_id to cafe_id.

2.2 Core API Endpoint Contracts

Public API

GET /api/v1/cafes/:cafeId/available-slots

Query: ?date=YYYY-MM-DD&time=19:00&partySize=N

Response: 200 OK { available_slots: [ { start_time: "19:00Z", end_time: "20:30Z" } ] }

POST /api/v1/cafes/:cafeId/reservations

Headers: Authorization: Bearer <JWT>

Body: { start_time, party_size } (Note: user_id is securely derived from the JWT)

Response: 201 Created { reservation_id, razorpay_order_id, status: "HOLD" }

Protected API (Requires JWT)

GET /api/v1/cafes/:cafeId/reservations

Response: 200 OK (Daily manifest for Host stand).

PUT /api/v1/cafes/:cafeId/reservations/:resId/status

Body: { status, version }

Response: 200 OK (Updates state) or 409 Conflict (OCC version mismatch).

HTTP Status Codes

201: Created successfully.

400: Invalid request payload.

401: Authentication required (Missing/Invalid JWT).

403: Permission denied (RBAC failure).

404: Resource not found.

409: Conflict (OCC mismatch or Transaction Write Conflict).

422: Unprocessable Entity (Business rule violation).

500: Internal server error.

2.3 The Table Allocation Algorithm (Best-Fit)

The engine utilizes a deterministic bounded search to optimize capacity.

Filter: Extract active, non-deleted tables with capacity >= party_size.

Overlap Exclusion: Query existing active reservations. Extract blocked table_ids. Remove from candidate list.

Single Fit: Sort remaining by capacity (asc), then by table_number (asc). Select the first table.

Merge Fallback: If no single table fits, generate combinations using can_merge_with arrays.

Constraint: Max depth of 3 tables.

Filter: Keep combinations where Σ(capacity) >= party_size.

Sort: 1) Lowest excess capacity, 2) Fewest tables, 3) Lowest starting table number.

Select: Top ranked combination.

3. Use Cases & User Flows

3.1 Customer Booking & Payment Flow

Search: Customer queries available-slots. Engine runs, returning open slots.

Lock (Transaction): Customer selects a slot. Backend opens a MongoDB transaction, runs allocation, verifies invariant Σ(capacity) >= party_size, writes Reservation as HOLD, and commits.

Intent: Backend generates Razorpay Order and transitions reservation to PENDING_PAYMENT. Returns order to client.

Payment: Customer completes Razorpay UI checkout.

Confirmation: Razorpay webhook triggers backend to verify signature and update status to CONFIRMED.

3.2 Host Stand Management Flow

Host views the shift manifest via a WebSocket connection for real-time updates.

Customer arrives. Host clicks "Check In" (status -> CHECKED_IN).

Host escorts to table. Clicks "Seat" (status -> SEATED).

Customer leaves. Host clicks "Complete" (status -> COMPLETED).

4. Edge Cases & Error Handling

4.1 Concurrency & Double Booking

Risk: Two users attempt to book overlapping intervals for the same table simultaneously.

Mitigation:
Double-booking prevention is guaranteed by the transactional availability check combined with MongoDB snapshot isolation and transaction retry semantics. The entire Read-Check-Write workflow executes within an ACID transaction. On an MVCC write conflict, the server automatically retries up to 3 times with exponential backoff before returning a 409 Conflict. Database indexes are used solely for query performance.

4.2 Payment Idempotency & Webhook Races

Risk: Webhook delayed, duplicate webhooks, or successful payment on a terminal state.

Mitigation:

Payment processor verifies payment_data.webhook_processed == true to ignore duplicates.

If a successful webhook arrives for a reservation in a terminal state (e.g., CANCELLED, EXPIRED), the State Machine explicitly blocks the transition. The payment is flagged for manual refund.

4.3 Last-Write-Wins (LWW) Data Corruption

Risk: Host A and Host B edit the same reservation simultaneously.

Mitigation: Optimistic Concurrency Control (OCC). Every mutation requires the client to pass the current version. The DB query executes UPDATE WHERE version = expected_version. Success increments version. Failure throws 409 Conflict prompting UI refresh.

5. Testing & Acceptance Criteria

5.1 Unit Tests

Allocation Engine:

Input: Max capacity 10, Party of 12. Expect: Exception/No Availability.

State Machine:

Attempt transition COMPLETED -> CONFIRMED. Expect: Exception.

Attempt transition HOLD -> PENDING_PAYMENT. Expect: Success.

5.2 Integration Tests

Concurrency Stress Test:

Fire 50 concurrent POST /reservations requests for a single 2-top table at 7:00 PM.

Acceptance: Exactly 1 request receives 201 Created. Exactly 49 requests receive 409 Conflict. Database contains exactly 1 document.

Transaction Retry Logic:

Mock MongoDB to intentionally throw TransientTransactionError during the commit phase for exactly 2 attempts.

Acceptance: The reservation succeeds on the 3rd attempt, verifying the retry block executes correctly.

OCC Conflict Test:

Fetch reservation (v1). Simulate two simultaneous PUT requests passing version: 1.

Acceptance: First request succeeds (v2). Second request fails with 409.

5.3 Boundary Conditions

Verify start_time and end_time logic across daylight saving time transitions.

Verify party_size: 0 or negative numbers are rejected by MongoDB JSON Schema validation before reaching the Express controller.
